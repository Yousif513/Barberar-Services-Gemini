# HQ-NEXT-04 synthetic access contract

The exact HTTP contract is [volabi-access-api.json](volabi-access-api.json). This slice is explicitly selected by `VOLABI_ACCESS_MODE=synthetic-guarded` and an external owned `VOLABI_ACCESS_ROOT`. The active launcher and default legacy instance remain unchanged and unenrolled under the approval hold. The legacy compatibility constructor/session behavior is not a claim that missing-data/recovery guards protect the active preview.

Only marked synthetic roots outside repository and `.local-volabi` paths can be initialized/adopted. Initialization creates no business sources and no normal session before saved-copy confirmation. Adoption is offline, requires a valid original legacy session through masked input, validates fixture proofs and supported schema, and preserves the exact original workspace/actor. Normal guarded open never creates directories, database, schema, guard, workspace or seed.

The only added SQLite schema object is exactly:

```sql
CREATE TABLE hq_access_state(id INTEGER PRIMARY KEY CHECK(id=1),schema_version INTEGER NOT NULL CHECK(schema_version=1),state TEXT NOT NULL CHECK(json_valid(state)))
```

`id=1`, `schema_version=1`, `state` is strictly validated versioned JSON control metadata. Its top-level fields are `version`, `instanceId`, `fixtureId`, `root`, `database`, `initialization`, `seats`, `sessions`, `permits`, `operations`, `challenges`, `attempts`, `receipts`. Verifiers, hashes, generations and pending proofs are confined here and in existing `sessions`; no extra indexes/triggers. Backup must accept exactly this new schema, exclude this entire table physically by rebuilding a fresh v1 sanitized database, and still exclude sessions. No guard/instance metadata may enter portable artifacts. Existing business tables/history remain unchanged except actual immutable access audit events in `events`.

Five-minute permits/challenges/stages, five invalid tries per challenge, thirty invalid attempts per instance per rolling fifteen minutes, thirty-day ordinary sessions. A factor is `vha1.<instance UUID>.<workspace UUID>.<32 random byte base64url secret>`. Scoped verifiers use SHA-256 with purpose, instance and seat separation. No plaintext token survives staging response or commit.

Access state and storage identity are rechecked for every request and again inside each write transaction. A private WeakMap binds each returned session object to its actual session hash; a retained JavaScript object cannot commit after revocation. Confirm atomically consumes stage/old generation, rotates factor, revokes same-seat sessions, creates one session and immutable event plus redacted receipt. An audit failure rolls back all security changes. Same material replay returns only receipt; replacement factor remains the reconnect path after a lost cookie response. Other seats stay unchanged.

Owner-only `ACCESS-GUARD.json` binds canonical root, directory and DB physical identities, fixture ID and instance ID. Guarded opens reject inert restores, links, insecure custody, wrong schema, replaced/missing files and inconsistent metadata; failed opens never adopt or repair. Bounded separate diagnostics record only diagnostic IDs, time and safe reason when database audit is unavailable. Same-OS-owner coherent tampering and the unavoidable OS rename window cannot be represented as cryptographic ownership assurance.

Physical device/inode identities are exact bigint decimal strings, including Windows inode values beyond JavaScript's safe integer range. Every guarded request and commit uses a fresh read-only SQLite header/instance metadata check as well as cached-handle and path/ACL checks, detecting same-inode overwritten files. Native Windows file locking is exercised by independent tests; no claim is made that JavaScript can eliminate the last OS path-operation race after its final check. A storage failure response says whether its separate diagnostic was actually recorded; an unsafe or missing root cannot receive a fabricated successful journal acknowledgement.

`ACCESS-SYNTHETIC.json` must already exist in an owner-only new external root: `{format:"volabi-access-synthetic-root-1",fixtureId:<UUID>,syntheticOnly:true}`. It is created independently by fixture setup, never by browser/bootstrap. Fresh init requires that marker alone. The CLI preallocates nonsecret operation, instance and seat IDs in an exclusive intent before creating storage. Only explicit `resume` can finish a missing/empty/partially created fresh schema after verifying its exact expected empty objects. A failed adoption transaction resumes only with the still-valid original session proof; it never falls through to fresh initialization. A committed pending instance can republish its missing guard or renew expired restricted bootstrap, with ordinary access still blocked. Active instances cannot be resumed as fresh initialization.

CLI: `node scripts/hq-access/cli.mjs init|adopt|permit --root <owned-marked-root>` or `resume --root <same-root> --operation <nonsecret-UUID>`. Only masked interactive stdin accepts session material; no credential flags or environment fields exist. The terminal deliberately displays only the newly issued restricted bootstrap or permit once, then metadata. The Access page handles first factor display and saved-copy confirmation. The fixture launcher is separate and never initializes anything.

Signout/revoke accept an in-memory client-generated UUID and 32-byte base64url operation proof, so the revoked caller can check its scoped receipt after a lost final response. Same operation with changed material conflicts. Replayed committed signout/revoke does not clear a newer cookie. Security events use bounded fixed system reasons and actual method labels; free-text reasons cannot become a secret-bearing log channel. Next development module reloads invalidate old cached store constructors and preserve safe error codes across constructor identity changes; unknown errors remain redacted.

Secrets belong only in labelled password fields, deliberate one-time display or masked CLI input. No URL/argv/env persistence, clipboard automation, browser storage or generic command payload. `returnTo` accepts only the existing HQ allowlist. The access page bypasses ordinary bootstrap; signed-out protected navigation cannot initialize a workspace in guarded mode.
