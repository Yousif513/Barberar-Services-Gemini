# Volabi local workspace — operator guide

Run `npm run hq:dev` from this isolated repair checkout, then open http://127.0.0.1:3113/hq. The launcher binds only 127.0.0.1 and opts this process into local development. Node 24.15 was verified; Node must support the built-in SQLite API. No Supabase, Tap or OpenAI credential is needed for this local loop. Vercel/cloud requests remain disabled even if the flag is supplied. Existing repair-branch deployment hold remains in force.

1. Compose a request with outcome, acceptance, limits, proposed owner/reviewer and actual linked sources.
2. Open its persistent task. Prepare a clearly labelled local evidence brief or write an actionable recommendation using exact selected source excerpts. Neither path activates or impersonates a company employee.
3. Inspect its recommendation hash, source versions and record-only scope, then record approve, decline or request changes with a reason.
4. Record the actual follow-up note and next action. Reloading the browser or restarting the process preserves the same workspace records while the local browser session remains valid.

An approval here records founder review only. It does not authorize or dispatch a refund, journal, fee change, employee, tool grant, invitation, recording, production merge or deployment. Changing request material or source evidence makes old material ineligible for approval/follow-up. A command with an uncertain response retains its identity and draft; recover that receipt before an identical retry. Never create a replacement identity merely because an answer was lost.

## Local data and limits

Requests, source snapshots, versions, receipts and application audit live in ignored `.local-volabi/hq.sqlite` with SQLite WAL files beside it. Keep the directory private. It is excluded from Git. The HttpOnly, SameSiteStrict browser cookie identifies one development workspace; clearing it or its 30-day expiry opens a new workspace, while prior local records remain on disk. After backend storage code changes, restart the owned local HQ preview before testing: hot reload can retain an old cached SQLite store class. Restarting the process preserves the database and workspace cookie. Production login, account recovery, backup/restore/export, retention/purge and multi-user access are not implemented here. Do not put production customer/financial data in this development workspace.

Lists are searched and paginated on the local server. Audit details minimize copied text/secrets and preserve immutable application history. The OS/database owner can alter local files; this is not tamper-proof regulatory storage. Binding the process to loopback is required; spoofable request headers are not a replacement for that network boundary.

Capability review: list/search/filter/detail/history, task creation/material revision, exact decisions, record-only follow-up, source intake/versioned correction and capability proposal inspection are required and implemented. Assignment is a proposed inactive design association. Bulk/import from external systems, export, business transitions, destructive deletion/restoration, saved views, permissions and operational execution are deferred beyond this approved local slice; no disconnected control promises them.

Verification commands: `npm run test:hq`, `npm run test:hq:browser` with the local server running, `npm run typecheck:mobile`, `npm run build --workspace=web_platform`, and `npm run lint --workspace=web_platform`. The complete regulated admin release gate is separate and remains blocked by its recorded release gaps.
