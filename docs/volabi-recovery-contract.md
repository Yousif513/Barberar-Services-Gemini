# HQ-NEXT-03 development recovery contract

Status: IMPLEMENTATION CONTRACT, frozen before implementation on 23 October 2026. Plan of record: `planning/volabi/RECOVERY_SCOPE_20261023.md` and its separate CEO approval. This tool is deliberately restricted to separately marked synthetic fixtures. It cannot back up or restore real Headquarters data, reclaim a seat, start a restored server, or resume a historical approval.

## Interface and custody

`node scripts/hq-recovery/cli.mjs create --fixture <existing-fixture-root> --output <new-output-directory>`; `inspect --package <existing-package> --output <new-output-directory>`; `restore --package <existing-package> --output <new-output-directory>`. All three require an interactive masked passphrase and the exact confirmation `SYNTHETIC ONLY`. No secret arguments, environment inputs, files, piping or default password. English CLI diagnostics accompany Arabic diagnostics by code; no browser UI is added. Library functions `createBackup`, `inspectBackup`, and `restoreBackup` take a transient passphrase Buffer for isolated automated tests. They never log it or put it in receipts; the caller owns clearing that Buffer. Operations resolve paths before access and refuse project/live-instance descendants, UNC/device paths, link/reparse components, hard-linked source/package files, existing output targets and source/output overlap. Scratch paths are children of a newly created owner-restricted output. CLI operation uses no network.

A fixture root must contain `fixture.json` declaring format `volabi-synthetic-fixture-1`, an unpredictable fixture ID, and an exact workspace/actor inventory. Every database workspace must contain a matching opaque `recovery-fixture-proof` record and version. This is an accidental-live-selection guard, not a defense against a malicious OS owner forging a fixture. The database name is fixed to `hq.sqlite`; no arbitrary SQL or source path is accepted. The source is opened read-only. No package contains fixture session rows or their SQLite pages.

## Bounds and envelope, version 1

Maximum encrypted package: 32 MiB. Maximum plaintext payload: 24 MiB. Maximum captured native snapshot: 64 MiB. Maximum rows in each logical table: 20,000; maximum total rows: 80,000. Maximum single serialized cell: 256 KiB; maximum JSON depth: 32; maximum JSON node count: 400,000. Maximum dependency files: 512; maximum one dependency: 8 MiB; cumulative dependency reads: 64 MiB. A stage has a 30-second deadline; the CLI watchdog ends an operation after 120 seconds with failure/cleanup-needed output. SQLite backup retries are bounded by that operation deadline and SQLite busy timeout. Input bytes, headers and KDF configuration are checked before derivation/allocation. Supported runtime Node 24.15.x; another runtime is an explicit incompatible-runtime refusal rather than an untested compatibility promise.

Binary envelope: 8-byte magic `VHQREC01`, 4-byte unsigned big-endian header length, canonical UTF-8 JSON header (maximum 1024 bytes), ciphertext, 16-byte GCM tag. Fixed header keys: format=1, cipher=`aes-256-gcm`, kdf=`scrypt`, N=32768, r=8, p=1, salt=16 random bytes base64, nonce=12 random bytes base64, plaintextBytes. The whole prefix including magic/header length/header is authenticated additional data. Scrypt uses 64 MiB maxmem, a 32-byte key and a 12–256-byte UTF-8 passphrase. Fresh salt and nonce per package. Authenticated decryption completes before JSON interpretation, schema rebuilding or extraction. The finite fixed KDF is deliberately not attacker-configurable. No archive compression or arbitrary members.

The payload is a fixed JSON object containing a versioned manifest, complete logical rows for six supported tables (sessions is empty), sequence high-water mark and a schema fingerprint. The allowlisted schema is rebuilt from trusted application-compatible DDL, never restored SQL. Current records, every version, exact command receipts and original audit fields/IDs/order are preserved as stored text. Opaque record kinds are retained. Unknown tables/indexes/triggers, missing/altered schema, malformed/cross-workspace links, missing versions, changed source hashes/citation pins and inconsistent receipts/watermarks refuse. Valid stale historical pins are checked against historical source versions, not rewritten to current values. Hashes of exact serialized rows bind all comparisons. A fresh sanitized rebuild excludes free-page/WAL session remnants; a known fixture authentication canary is additionally scanned in the sanitized native database.

## Capture, dependencies and failures

Use Node's supported SQLite online backup with a read-only source connection for one coherent committed cut including WAL. The backup snapshot is a sensitive temporary file; it is validated and sanitized into logical rows then removed before publication. No source checkpoint, journal reset or live-file copy. Dependency capture is separate and uses explicit project-owned reference allowlists: store/boundary/Council/Projects/catalog source contracts and portraits/voice files. Package includes hash references, not asset bytes. Referenced installed-skill pins in records are included as externally unresolved metadata rather than reading the global home or fabricating availability. Capture detects changing allowlisted files; verification reports missing/mismatched/externally-unverified dependencies. Data integrity and dependency completeness are separate results; an overall full-fidelity result requires both. Code commit/dirty status and runtime are recorded, with no shell, credential or environment enumeration.

Owner-only directories use mode 0700 on POSIX; Windows uses an inheritance-disabled ACL containing only the current SID, set and checked with native PowerShell/.NET. If custody cannot be established, refuse before plaintext. Output files use exclusive creation and atomic no-clobber hard-link publication; a final package is usable only with a matching success journal and receipt. Each operation writes a separate redacted journal with its actual outcome, snapshot cut and package digest. No mutation is inserted into captured events. Journal/report failure removes newly published artifacts where possible and returns failure; incomplete attempts are not usable. Failure diagnostics contain codes, not input records or passwords. Interrupted staging leaves a clearly named `INCOMPLETE.json` and controlled root; the runbook gives checked cleanup instructions. Normal deletion is not forensic erasure. Cleanup is restricted to newly created owned staging files, never source databases or earlier output directories.

Restore rebuilds a new database, creates an inert marker, verifies through a read-only SQLite connection, then closes it. It creates zero sessions, has no HTTP/command execution entry point and preserves historical actors/decisions as data. HqStore refuses an inert marker even if an operator tries to use it. The report stores counts/digests/status, never bodies. Existing live instance, cookies and application startup stay unchanged. Read-only verification is not seat reclamation or a production disaster-recovery certification. A same-disk package is not off-device redundancy; lost passphrase means lost access.

## Acceptance evidence

Owner tests start red then exercise representative two-workspace fixtures through existing HqStore commands: tasks, recommendations, decisions, follow-up, Projects/milestones/closure, Council preparation/minutes/dissent/correction/cancel/reopen, classified/unknown sources and transitive pins. Assertions compare exact complete tables and sequence; preserve Arabic/English/emoji/CRLF UTF-16 citations; include committed WAL and uncommitted writes; prohibit sessions and token canaries; use a post-capture sentinel; verify inert marker, immutable history and allocator continuity on a separate derivative. Adversarial tests cover authentication/tag/header/truncation, schema, history/links/hash corruption, paths/links/no-clobber, bounds and truthful failure/journal cleanup. Independent reviewers execute their own cases. Root additionally runs existing app regression/build/mobile/lint and reports the unchanged regulated release gate honestly. No actual Headquarters backup or restore occurs in acceptance.

Sources consulted: official Node v24.15 SQLite online backup and crypto AES-GCM/scrypt API documentation, existing local store and Council/Project invariants. Any unimplemented acceptance obligation remains a named failure, not an implied pass.

## Completion and security-review clarifications

An encrypted package is portable as a set: `backup.vhq`, its creation `receipt.json`, and `journal.json`. Keep these three metadata-linked files together; an `INCOMPLETE.json`, absent/mismatched creation metadata or altered digest causes `package_not_complete`. Receipt/journal provide local crash-consistency evidence under the OS owner's custody, not a second cryptographic signature or creator identity. The envelope authenticates content to the passphrase. Metadata is checked only after envelope authentication and payload validation, so malformed authenticated data cannot be mistaken for an ordinary publication failure.

Windows uses native .NET ACL APIs through a parameter-safe encoded PowerShell invocation; no optional PowerShell module dependency. Native reparse checks are batched for dependency files, with per-file lstat/handle identity checks retained. Custody protects against other unprivileged accounts and accidental path selection. A malicious process running as the same OS owner or administrator can alter files/ACLs and is outside this local tool's guarantee. Internal consistency detects dangling, mismatched or incomplete retained history; without a previously trusted independent snapshot digest it cannot prove that an attacker coherently deleted all related historical rows and receipts.

Convenience entry point: `npm run hq:recovery -- --help` prints the bounded CLI usage. The CLI's supervised worker has a hard 120-second deadline for synchronous crypto/JSON/SQLite work, and interrupted-run cleanup verifies the operation UUID and owner custody before touching known files. Trusted library tests use stage-deadline checks; they do not claim an interruptible synchronous library API.

SQLite's readonly snapshot inspection can leave WAL and shared-memory sidecars on Windows even after closing its connection. All owned scratch databases (`snapshot.native`, `sanitized.native`, `restore.stage`) therefore have an explicit four-file lifecycle: main file, `-journal`, `-wal`, `-shm`. Connections close before checked cleanup; successful create publishes no raw sidecar. Success, failure and interrupted-run paths use the same finite member inventory. Final create artifacts are exactly the encrypted package and its two redacted completion metadata files. Restore retains only its inert database, inert marker and two redacted completion metadata files. Failed cleanup cannot be labelled complete. Independent sidecar regression supersedes the initial owner result until rerun.

Primitive known-answer checks use [RFC7914 section12](https://www.rfc-editor.org/rfc/rfc7914.html#section-12) and [NIST GCM-AES256 example2](https://csrc.nist.gov/CSRC/media/Projects/Cryptographic-Standards-and-Guidelines/documents/examples/AES_GCM.pdf). These verify runtime primitive outputs alongside independently decoded envelopes; they are not algorithm certification.
