# HQ-NEXT-03 — local backup and isolated recovery verification

Status: PROPOSED FOR CEO APPROVAL. Prepared 23 October 2026. Scope only: no backup, restore, recovery command, recovery UI or live database inspection has been performed for this proposal. The first loop, Projects and Council remain the delivered baseline; Headquarters is still under development.

## Outcome and first-slice boundary

Produce a manually initiated, encrypted local backup of the complete local HQ instance and demonstrate that its records can be recovered faithfully in a separate, inert test location. The operator receives a source-linked verification report with explicit failures and limitations. This is recovery of records for inspection and validation, not resumption of HQ operations.

The first slice is a development-only local CLI/runbook, not a browser export or new dashboard route. It has three operations: create an encrypted backup; authenticate/inspect a package; restore into a new isolated directory and produce a verification report. Each refuses an existing target. No scheduling, cloud storage, public upload, email, production database access, live replacement, merge or deletion of old backups. The ordinary HQ navigation and approved visual system remain unchanged. A later recovery dashboard needs its own scope approval.

The local SQLite file contains multiple workspaces. The package deliberately covers the whole instance, with workspace boundaries retained, and is therefore sensitive administrative material. It must never be downloadable through a normal workspace session or presented as that person's workspace-only export. Approval of this scope authorizes development of this whole-instance mechanism, not distribution of its contents or a live-data backup drill. Initial acceptance uses synthetic isolated fixtures only. A real-data backup or operator recovery ceremony is a later explicit action, with no secrets requested now.

## Evidence and discovered gaps

The source inventory in RECOVERY_SOURCE_INVENTORY_20261023.json pins the inspected code and contracts at the planning baseline. HqStore uses Node SQLite with WAL, synchronous FULL, foreign keys and transactional command receipts. The handler selects `.local-volabi/hq.sqlite` and caches the store by resolved path. Tables are workspaces, sessions, records, record_versions, commands and events, with immutable-history triggers and SQLite's event sequence allocator.

The current session cookie is an expiring bearer credential; a fresh session creates a fresh workspace rather than reconnecting to old records. Consequently, copying a database is not a secure account recovery system. Current startup can create a missing database/schema, which could appear to be an empty installation. These are verified gaps. This slice must not offer a workspace chooser, import session hashes, start HqStore against a restored file, or describe a successful drill as secure founder-account recovery. Designing seat reclamation and detecting loss of a previously initialized live installation remain explicit follow-on items before live adoption.

Current catalog inputs live outside the database: persona/role/skill contracts, source excerpts, installed skill metadata and media. An intact SQLite file alone does not establish that these dependencies are present, unchanged, licensed or behaviorally evaluated. Existing business permissions and employee activity are not derived from a recovered identity or old approval.

| Audit/history | All scoped and instance-wide historical events, original actor attribution, IDs, timestamps, details and original ordering; all record versions and sequence high-water mark. No truncation to UI pagination or latest 100 events. |
| Dependency inventory | Schema fingerprint/version, runtime and tool versions, repository commit and dirty-state indication, catalog/static asset/skill hashes and allowlisted relative references. Missing or mismatched dependencies explicitly block a full-fidelity result. |

Preserve every workspace and every record kind, including opaque kinds the supported schema permits; never silently drop an unrecognized kind. Unknown schema structure, migration requirements, executable triggers or incompatible runtime fail closed with a named reason. No guessed down-migrations. Preserve exact serialized bodies rather than reparsing and normalizing text. Preserve sqlite_sequence's event high-water mark, even where deleted/other scoped events would make IDs non-contiguous. Cross-workspace links must fail validation rather than be reassigned.

Exclude all sessions and authentication token hashes, cookies, CSRF tokens, environment files, provider credentials, encryption secrets, raw global-home contents, generated caches and unrelated repository files. This is an operational-secret exclusion contract, not automatic DLP: exact source bodies may contain user-entered sensitive text or secrets. Never silently redact history or certify that arbitrary prose contains no secrets; classify the entire package as sensitive, disclose this limitation and keep real-data use separately held. Sanitization is a fresh database rebuild from an explicit supported schema and validated snapshot records, excluding the sessions table's rows; deleting session rows in a raw database copy is insufficient because free pages/WAL may retain them. The resulting package must contain no raw captured SQLite pages or unredacted snapshot sidecars. A controlled temporary native snapshot is sensitive plaintext and follows the cleanup contract below.

Bundle only allowlisted, redistributable project-owned dependencies whose inclusion is justified and bounded. For global skills and other external dependencies, retain hash/provenance references and report missing or mismatched content. Do not copy entire global skill directories, reinstall packages, download models, invoke voices or invent an exact historical dependency. A data-integrity pass may coexist with a blocked dependency-completeness result; the overall result must show that limitation.

## Capture, encryption and custody

Use a supported SQLite online snapshot primitive to obtain a coherent committed cut including WAL-resident commits. Node v24.15.0 exposes `node:sqlite` backup; its exact behavior and failure handling must be checked against local/runtime or official documentation before implementation. Never copy the live main file alone, concatenate WAL files, reset a journal or force a destructive checkpoint. Snapshot capture must not interrupt or partially include a concurrent multi-record command.

Record snapshot ID, capture interval, schema fingerprint, per-table/workspace counts, event watermark and authenticated content digests. Enumerate live dependency inputs into a stable capture manifest; detect files changing during capture and fail/retry within a finite bound. Do not claim atomicity across SQLite and arbitrary files. Report the database cut and dependency-check interval separately. Final artifact publication is atomic/no-clobber: an incomplete attempt cannot be listed as a usable backup.

Use a versioned authenticated-encryption envelope and vetted platform cryptography; no custom cipher. Proposed implementation contract: AES-256-GCM with a fresh random salt and nonce per package, scrypt-derived key, explicit bounded KDF parameters, authenticated format/schema metadata, and test vectors. Independent security review must validate nonce/key handling and password input before acceptance. The passphrase is masked in a local interactive prompt; never a command-line argument, environment variable, chat message, file tracked in Git, diagnostic, command receipt or log. Passphrase custody is separate from the package; no key escrow or recovery promise if it is lost.

Authenticate before interpreting/extracting package contents. Wrong passphrase, altered metadata/ciphertext/tag, truncation and unsupported format produce a clear refusal without publishing plaintext or overwriting a target. Permit only fixed allowlisted member names; no executable content, arbitrary extraction path or user-provided SQL. Limit file sizes, record counts, KDF memory/work, nesting and processing time before allocation. Document finite supported bounds and refusal messages before coding; overflow must not silently truncate. No compressed archive is necessary for this first slice.

Use owner-restricted OS directories outside public assets and version control for sensitive snapshots, packages and drill output. Read-only access to the legitimate source database and allowlisted dependency files inside the repository is permitted. All staging, package-output and restore destinations must be outside the repository/live-instance root. Resolve canonical paths and reject absolute/UNC/member traversal, symlink/junction/reparse-point escapes, destination overlap with those roots and source/destination aliasing. Recheck ownership before recursive cleanup. Protect staging while it exists; on failure or interruption record a visible cleanup-needed state with safe retry instructions. Ordinary deletion is not a claim of forensic erasure. Never delete the source database, audit history or prior packages as cleanup.

Backups on the same disk do not protect against disk loss. This slice provides no off-device replication or disaster-recovery certification. Recovery point is the last successfully verified backup's actual capture boundary; recovery duration is measured in the drill. No invented schedule, zero-data-loss promise or production recovery SLA.

## Isolated restore drill — required sequence

1. Create an owned fixture instance in a temporary root, with at least two workspaces and all current record kinds. Populate through supported fixture/command helpers: task/recommendation/decision/follow-up; project/milestone/closure; Council preparation/minutes with dissent and correction; restricted/private/unknown sources and transitive pins; stale/current dependencies; refusal/audit and command retry/conflict cases. Fixture identities are synthetic development actors, never activated management employees.
2. Establish a pre-capture fingerprint. Exercise committed WAL data and a competing transaction with multiple linked writes. Capture must correspond to one complete committed state: committed records present, uncommitted changes absent, no torn task/receipt/audit combinations. Exclude session hashes from the sanitized package and detect a known authentication canary in logical content and raw package plaintext before encryption.
3. Encrypt and publish one fixture-only package. Change the source fixture after capture with an unmistakable sentinel. Capture the new live-fixture logical state and file identity. The recovery operation must not roll this newer source back or acquire its session.
4. Authenticate/inspect the package into a new, no-clobber owned test location. Restore without constructing the application store or starting an HTTP server. Open only through a read-only validation connection; disable command runners, startup seeding, model/tool execution, microphone, audio and outbound integrations. Historical workspace ownership is preserved as data; no session is issued or rebound.
5. Compare the complete restored instance to the captured baseline: exact serialized record/version/receipt/event values and IDs; all workspaces; source/citation hashes and ranges; parent/decision/project/Council links; classification and stale-state invariants; schema indexes/triggers/foreign-key checks and SQLite integrity checks; global sequence watermark. Reject orphaned, cross-workspace or contradictory relations. Do not require contiguous audit IDs.
6. Demonstrate isolation: source fixture sentinel/logical state/file identity remain unchanged during restore; normal live cookies, old captured tokens and invented workspace/actor claims cannot open or mutate the restored artifact. The restored verifier has no HQ HTTP session or command execution entry point. Separately test any invocation/wrapper rejects requests to start or write through HqStore. Inspection of private records is confined to this local administrative test report, with no browser/API exposure.
7. Validate behavior only in a second disposable derivative fixture if needed for constraints/idempotency tests. Label those new test mutations separately; never modify the recovered historical evidence or treat an old approval as a new authorization. Verify immutability triggers, duplicate command receipt behavior, conflict rejection and allocator continuity without replaying business effects.
8. Run the adversarial matrix below, publish a redacted verification receipt and clean only the owned temporary plaintext roots. Package and report retention remain explicit; no automatic deletion of retained packages. Report cleanup failure as failure/attention required, never a clean pass.

Backup completion occurs after the captured cut. Its local recovery-journal receipt links that earlier cut and final package digest; do not insert a completion event into immutable captured history or claim it was already inside the snapshot. Journals log only operational metadata, never source bodies or keys. If journaling/publication fails, the attempt is incomplete and retry semantics must avoid duplicate usable artifacts.
