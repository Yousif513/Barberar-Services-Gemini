# HQ-NEXT-04 — local founder-seat continuity and storage-loss detection

Status: PROPOSED FOR CEO APPROVAL, 23 October 2026. Scope only; no application implementation, screen rendering, credential issuance, real-data inspection or account-seat reclamation. HQ-NEXT-03 remains the accepted synthetic recovery baseline. Full Headquarters remains under development.

## Outcome and approval boundary

An enrolled local operator can reconnect to the exact existing development workspace after a cookie expires, without creating a replacement workspace, rewriting its history or expanding its authority. Normal startup refuses missing, replaced, unsupported or inert storage. Explicit initialization is a separate operation for a genuinely new synthetic instance.

Approval of this proposal would authorize code and tests against isolated, positively marked synthetic fixtures only, including an isolated browser server on a different port. It would not authorize applying the guard/migration to the current preview, enrolling or reclaiming a real founder seat, opening real HQ files, copying real cookies, or changing the active launcher/data root. Those are a later concrete approval after independently verified evidence. No real credentials are needed for this build.

“Founder seat” means custody of one previously enrolled local workspace/actor pair. It does not verify a person's legal/CEO identity, create a company role or grant production permissions. A recovery credential proves prior local enrollment, not business authority. A valid old browser session alone is insufficient to enroll a new recovery factor: enrollment also needs a short-lived permit from the local development operator.

## Verified code gaps and retained safeguards

- `local-store.mjs` constructor creates its directory, opens writable SQLite and applies CREATE IF NOT EXISTS. Missing storage is not distinguished from a new installation.
- `createSession()` allocates new workspace and actor IDs every time it is called. `getSession()` accepts a valid unexpired token for 30 days. There is no durable enrollment or reconnect operation.
- `handler.mjs` calls createSession on POST `/api/hq/session` whenever the cookie is invalid/missing. The React provider automatically calls that operation. “Retry” can consequently create a different empty workspace instead of recovering the old one.
- The store is cached by file path. Checking only once at process startup would miss disappearance/replacement during a running process.
- Existing loopback/origin checks, HttpOnly/SameSite cookie, CSRF, workspace-scoped commands, immutable history, record-only decisions and HQ-NEXT-03 inert-restore refusals are retained. They are useful boundaries, not CEO identity verification.

These findings come from source only. No assertion is made about the current preview's cookies, database existence, contents, ownership or recoverability.

## Ownership and credential contract — proposed technical choices

1. Explicit synthetic initialization uses a local CLI in an owned new root outside repository/live paths. Require the independent fixture marker and opaque workspace proof used by the recovery tests; do not treat an environment variable alone as permission. Use a no-clobber creation protocol. Initialization binds a new instance ID, physical database identity/canonical path and original workspace/actor pair. A successful fresh initialization must finish verified credential enrollment before normal access is enabled. Pending/partial initialization stays blocked and can only be resumed in the same owned fixture; it cannot appear as a clean installation.
2. For an existing synthetic workspace, the CLI can issue a five-minute, single-use enrollment permit bound to the exact instance, workspace, actor, purpose and credential generation. Issue only with explicit local-operator confirmation of that opaque fingerprint. The browser must independently possess the current matching session and CSRF proof. A permit alone cannot enroll or log in; a cookie alone cannot enroll. Permit fields never let a caller nominate another workspace at the HTTP boundary.
   Bootstrap ordering is explicit. A fresh fixture initializer validates its independent synthetic marker, uses exclusive no-clobber root/database creation, establishes the new workspace/actor plus schema/guard in a pending initialization, and issues one five-minute bootstrap proof bound to that operation/instance/seat. Workspace proof records are generated as part of this explicit initialization, not required to exist inside a database before it is created. The external marker and selected owned root are required beforehand. No business records or general session are created. Bootstrap proof reaches only enrollment endpoints and the Access page, never ordinary HQ reads/commands. Saved-secret confirmation atomically activates enrollment and issues the first normal session; a pending/failed guard publication remains blocked until the same initialization operation is explicitly resumed.

   Existing legacy synthetic fixture adoption is a distinct offline CLI operation with the fixture server stopped. Validate the synthetic marker and supported schema, then accept a still-valid legacy session secret through masked input only; resolve its hash to the original workspace/actor before changing schema/guard. No choice of a workspace by name/order or caller-supplied actor substitutes for that proof. The CLI creates a pending instance binding and versioned additive schema with redacted adoption intent, preserving exact existing business/history data, and issues a restricted five-minute bootstrap proof for that proved seat. No normal session is issued until saved-secret confirmation. Missing/expired legacy session or failed source validation refuses adoption. Partial guard/schema publication is a blocked resumable operation, never automatic repair. An existing valid guard uses the ordinary session-plus-permit enrollment path; it is not legacy-adopted again. Fresh creation and legacy adoption cannot share a permissive fallback.

3. Generate recovery credentials with 32 cryptographically random bytes; encode as a versioned copyable token with a nonsecret instance/seat selector and a secret component. Store only a cryptographic verifier with domain/purpose separation; never reversible secret text. Treat possession as a local bearer recovery factor and explain safe separate custody. This is not MFA certification or a recoverable password vault. No names, birthdays, record knowledge, arbitrary workspace UUID, port ownership or “oldest/only workspace” rule can establish ownership.
4. Enrollment, recovery and rotation have an explicit short-lived pending phase. Show the proposed replacement secret once in a no-store response, require re-entry to confirm the separately saved copy, and issue no new general HQ session from staging. Prior valid sessions retain their normal scoped authority until confirmed revocation/commit; restricted bootstrap still has no general session. Five-minute expiry/cancel consumes only the staging operation. During recovery/rotation the old credential remains valid until final atomic commit, preventing response loss before confirmation from destroying the only factor.
5. Confirmed recovery is a single SQLite transaction: recheck instance/seat/purpose/expiry/generation/proof, consume operation and old recovery generation, store new verifier, revoke every old session for that workspace, create one fresh session and CSRF binding, and append a reasoned immutable security event/receipt. Workspace and actor IDs stay identical. Other workspaces/sessions are unchanged. Enrollment/rotation/revocation apply equivalent atomic rules. An audit persistence failure rolls back the security change.
6. Session token hashes and recovery generation are checked at every server request and again inside the write transaction. A request queued before revocation cannot commit afterward with stale authority. Cached store/session objects confer no durable authorization. Session lifetime remains the existing 30-day development policy unless a later approved policy changes it; recovery staging/permit lifetime is five minutes.
7. Handle lost final response honestly. Persist a redacted operation receipt keyed by an unguessable operation ID and scoped proof, never a plaintext session/recovery token. Same operation/material retry produces the same state transition, not another workspace or rotation. If a cookie was not delivered after committed recovery, the operator uses the replacement credential whose custody was confirmed. Never resurrect the consumed factor or silently perform a second recovery. Conflicting concurrent confirmations have exactly one winner; a stale operation cannot revoke a newer credential/session.
8. Bound unauthenticated parsing to 4 KiB, one active staging operation per seat and five attempts per challenge; use a persistent instance-wide cap of 30 invalid attempts per rolling 15 minutes. Restart does not reset this budget. Unauthenticated challenge issuance is instance/browser scoped and does not reserve, cancel or replace a seat staging operation or reveal whether a selector exists. Reserve the seat operation only after validating its current recovery factor, ordinary session plus enrollment permit, or narrow bootstrap proof. A pending operation never revokes prior sessions before confirmed commit. Do not let an unauthenticated caller permanently lock a chosen seat; all invalid/unknown selectors have the same external refusal and no public seat listing. Implement finite challenge expiry/cleanup and bounded logs. Successful normal sessions are not globally disabled by an attack. A later local-operator cooldown reset must be explicit, synthetic-only and audited, never an automatic bypass.
9. Secrets are allowed only in masked terminal input or labelled password fields and deliberate one-time credential display. Never argv, environment variables, URLs, telemetry, console logs, reports, Git, localStorage/sessionStorage, generic task/decision payloads or source evidence. No clipboard auto-copy, automatic download or third-party script on the access flow. Retain current same-origin/loopback rules; verify a pre-auth browser challenge with Origin checks for recovery, current CSRF for authenticated changes, no permissive CORS, and cookie protections. Local HTTP is a development boundary, not Internet transport security.

## Storage guard and failure semantics

Normal startup never creates a database, directory, workspace, schema, source seed, guard or ownership record as a repair. It resolves the configured canonical instance root, validates its owner-only guard and physical database identity/instance metadata, rejects reparse/junction/hardlink aliases and inert restore markers/application ID, then opens only an existing supported store. Schema upgrades require the separately authorized synthetic enrollment/initialization operation, not constructor side effects. Missing both guard and database still does not mean permission to initialize.

| State | Required behavior |
|---|---|
| Not explicitly initialized | Refuse normal start. Offer nonsecret setup guidance for a new isolated synthetic root; no create-on-open. |
| Expected DB missing, empty/truncated, unreadable or corrupted | Stop data/session commands; preserve all remaining files, exact safe reason and diagnostic ID; no fresh database, seed, workspace or success response. |
| Guard missing/altered; database replaced; instance/path mismatch; unsafe ACL/path | Refuse access without repairing, rebinding or trusting a supplied file. No browser account enumeration. |
| Legacy/un-enrolled store | Refuse automatic adoption. Fixture-only enrollment requires current seat proof + local permit. A lost-cookie legacy real seat has no supported recovery in this slice. |
| Inert HQ-NEXT-03 restored artifact | Continue to refuse, including a moved DB without its marker. No conversion into an active instance. |
| Valid instance, no valid cookie | Access required; no workspace creation, no anonymous domain data. |
| Valid instance and session | Normal scoped record-only loop; unchanged inactive identities and business holds. |
| Storage lost/replaced while server is running | Revalidate guard/file/instance identity before every request and write commit, including cached handles; stop new operations. Drain/close affected handles, surface unavailable and preserve uncertain outcome receipts. Never keep serving an orphaned cached DB as the authoritative instance. |

A guard under the same OS owner is an accident/replacement detector, not a signature proving CEO ownership or protection against an administrator coherently changing all files. Check file identity and bounded header/instance metadata rather than hashing a changing entire database on every request. No repair tool searches disk or follows a new path looking for a replacement. Failure diagnostics use no secret/source bodies; if the DB cannot persist audit, write a bounded owner-restricted separate diagnostic journal without fabricating a historical business event. If that also fails, visibly refuse rather than claim successful recording.

## Data, audit and HQ-NEXT-03 compatibility

Keep original business records, all versions, command receipts, source/classification pins, historical decisions and audit IDs unchanged. Security controls may add versioned instance/seat/credential-generation/pending-operation/attempt/receipt metadata in the same SQLite transaction domain; do not change role definitions or impersonate historical actors. Each security event records operation ID, prior/resulting generation, original actor/workspace, actual authentication method, time, reason and outcome; no verifier/token/cookie text. Before authentication, diagnostic actor is unverified, never “CEO”.

New security schema is an explicit versioned dependency of this slice. Extend the backup schema validation/sanitization deliberately: old v1 fixture packages remain inspectable, supported new fixture schema preserves every business/history field, and sessions, credential verifiers, pending permits/proofs/rate state and new login-capable instance metadata are physically excluded from portable artifacts. Restore stays inert and non-enrollable. Unknown schema refuses; do not weaken schema checks or silently drop an unfamiliar table. Independent tests inspect raw sanitized pages as well as logical rows. Existing HQ-NEXT-03 freeze receipts remain historical; publish fresh reviewed hashes for changed code.

List/search/bulk/import/export/delete/merge/reassign of seats are not required for one-seat recovery. No workspace picker, ownership transfer, “make me CEO”, recover-by-agent or generic CRUD. Sign-out/revocation/rotation are explicit commands with safeguards and audit; no destructive data deletion. Operational failure never grants a fallback role.
