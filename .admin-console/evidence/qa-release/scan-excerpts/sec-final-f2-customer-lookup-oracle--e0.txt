    1: -- F2 (docs/reviews/2026-10-16-security-final-recheck.md): admin_privacy_find_customers was an unthrottled oracle. Substring
    2: -- matching on phone digits and e-mails let an operator rebuild a full number or address one character at a time despite the
    3: -- masking, and the audit row carried no trace of the query, so the probing could not be seen. Now:
    4: --   * a phone lookup matches the whole number only (normalised: spaces, +, 00, the 966 country code and a leading 0 removed;
    5: --     at least 9 digits), and an e-mail lookup the whole address only (case-insensitive equality, never a substring);
    6: --   * a name lookup (at least 3 characters) matches the first and last name only, never the e-mail;
    7: --   * results are masked: first name, last-name initial, e-mail as x***@domain, last 4 phone digits, join date;
    8: --   * step-up (a fresh authenticator code) is required;
    9: --   * per actor at most privacy_lookup_limit() (10) lookups in privacy_lookup_window() (10 minutes); the next one is refused,
   10: --     recorded, and raises one 'privacy_lookup_limit_reached' security alert for the owners in the window;
   11: --   * every lookup, refused or not, is audited with the kind, the length and an HMAC-SHA256 of the normalised query under a key
   12: --     no client role can read, so repeated or stepwise probing shows in the log without the log holding the personal data.
